# Тестирование, ревью и Definition of Done

## Стратегия тестов

Тесты проверяют наблюдаемый контракт, а не копируют реализацию.

- Изменение поведения покрывается тестами в том же изменении.
- Исправление бага содержит сценарий, который воспроизводит дефект.
- Рефакторинг выполняется только при достаточном существующем покрытии.
- Предпочтительно проверять состояние после действия; число и порядок вызовов — когда поведение само является контрактом.
- Для изолированной логики подходят unit-тесты, для взаимодействия слоёв — быстрые integration-тесты с фейками внешних зависимостей.
- UI/E2E нужны для сценариев, которые нельзя подтвердить нижележащими тестами; они не заменяют быстрые проверки.
- Не тестировать геттеры, возможности языка и библиотек, простое делегирование или точную копию алгоритма тестируемого класса.
- Не расширять публичный API только ради теста.
- Асинхронность проверять контролируемым временем/планировщиком, а не реальными задержками.

Новые тесты создаются по существующим соглашениям проекта. Если тестовой инфраструктуры нет, не добавлять её без запроса; проверить сценарий доступным стандартным способом и явно отметить ограничение.

## Самопроверка перед ревью

1. **Соответствие:** изменение делает именно то, что заявлено.
2. **Дизайн:** решение находится в правильном модуле и не нарушает границы проекта.
3. **Полнота:** учтены все члены контракта, обёртки, потребители и миграционные шаги.
4. **Функциональность:** проверены граничные случаи, ошибки и конкурентность там, где они применимы.
5. **Простота:** нет спекулятивных абстракций и побочного рефакторинга.
6. **Тесты:** поведение и регрессия покрыты по правилам проекта.
7. **Имена и комментарии:** имена ясны; комментарии короткие и не устарели.
8. **Публичный API:** изменение согласовано с версией и потребителями.
9. **Документация:** README, reference, ADR и инструкции обновлены, если изменение их делает неверными.
10. **Финальное состояние:** diff/status содержит только нужные файлы, стандартные проверки запущены на итоговом состоянии.

## Как формулировать замечания

- Сначала проверить чужое замечание против текущего кода и документации; не соглашаться автоматически.
- Описывать проблему и механизм её влияния, а не автора.
- Обязательные замечания отделять от необязательных: `Nit:`, `Optional:`, `FYI:`.
- Если известен конкретный минимальный вариант исправления, предложить его.
- При закрытии обсуждения указывать, что исправлено или почему изменение не требуется.
- Не выдавать гипотезу за подтверждённый дефект.

## Definition of Done для изменения

- [ ] Запрошенный сценарий работает на финальном состоянии.
- [ ] Существующие относящиеся к изменению тесты проходят.
- [ ] Новое поведение и исправленный баг покрыты согласно правилам проекта.
- [ ] Стандартные build/test/lint запущены там, где они покрывают изменение.
- [ ] Внешний контракт, миграция и затронутые потребители проверены.
- [ ] Документация и комментарии соответствуют новому поведению.
- [ ] Проведён самостоятельный review diff/status.
- [ ] Лишние артефакты текущей работы удалены.
- [ ] Непроверенные части и блокеры явно перечислены.
- [ ] Ревью, QA и merge выполнены, если входят в процесс команды и запрос пользователя.

Формальный статус задачи, апрувы и релевантные QA-критерии определяются командным процессом. Агент не меняет их во внешних системах без явного разрешения.
