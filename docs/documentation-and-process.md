# Память, рабочие документы и постоянная документация

## Три разных типа информации

### `memory/` — устойчивые сведения

Только факты, нужные в будущих задачах: карта проектов, назначение репозиториев, согласованные способы доступа и ссылки на источники. Не хранить секреты и хронологию работы.

### `process/` — временная работа

```text
process/<TASK-KEY>/
  design.md
  plan.md
  log.md
  next-steps.md
```

Для работы без ключа используется `process/<short-name>/`.

- `design.md` нужен при выборе между вариантами, исследовании или изменении контракта.
- `plan.md` — для цепочки шагов с проверками и статусами.
- `log.md` — для изменений, длительных и многосессионных задач.
- `next-steps.md` — для передачи работы в новую сессию или другому исполнителю.

Для простой задачи документы не нужны. Для одноразового read-only ответа log/backlog не создаются без запроса.

### `backlog/` — кандидаты в отдельные задачи

Посторонняя находка сначала сообщается пользователю. В backlog она записывается, только если полезна для будущей работы или пользователь попросил. Внешний тикет создаётся только с подтверждением.

## Журнал

Запись журнала содержит:

- дату и цель;
- затронутые проекты и файлы;
- подтверждённые выводы и источники;
- проверки с результатами;
- блокеры и непроверенные части.

Это не дневник рассуждений и не место для backlog. Старые журналы не удаляются автоматически.

## Постоянная документация

Документация описывает текущее состояние, отвечает конкретному вопросу и не дублирует другой источник истины. Обновляется вместе с поведением.

Используются четыре вида [Diátaxis](https://diataxis.fr/):

- Tutorial — ведёт читателя от начала до изученного результата.
- How-to — решает конкретную практическую задачу.
- Reference — даёт точный факт, параметр, команду или правило.
- Explanation — объясняет устройство и причины решений.

README остаётся коротким обзором: назначение, требования, сборка/запуск, тесты, модули, CI/публикация и ссылка на подробную документацию. Подробные страницы можно хранить в `documentation/{tutorials,how-to,reference,explanation,adr}/`, если это соответствует проекту.

## ADR

ADR нужен для значимого решения с альтернативами и последствиями. Используйте [шаблон](../templates/adr.md) или формат проекта, например [MADR](https://adr.github.io/madr/).

- В ADR фиксируются контекст, варианты, решение, причины, последствия и участники принятия.
- Предложенный ADR проходит обычное ревью.
- Принятый ADR не переписывается задним числом. Новое решение оформляется новым ADR, старый получает статус заменённого или устаревшего.
- После завершения большой задачи постоянные решения переходят в ADR, итоговое устройство — в reference/explanation. Временные документы обрабатываются по процессу команды.

Шаблоны рабочих документов находятся в `templates/process/`.
