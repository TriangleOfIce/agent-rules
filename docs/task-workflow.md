# Маршрут выполнения задачи

## 1. Понять запрос и ограничения

- Сформулировать ожидаемый результат, границы и способ проверки.
- Найти проект по `memory/projects.md`, если карта существует.
- Прочитать инструкции затронутого репозитория и подкаталога, README и настройки агента.
- Учесть явные решения пользователя. Не подменять их рекомендациями из старых документов.
- Если варианты понимания приводят к существенно разным решениям, задать вопрос с рекомендуемым вариантом.

Результат: понятно, что именно должно измениться и как это проверить.

## 2. Исследовать существующее решение

- Найти реализацию, потребителей, тесты и стандартные команды проекта.
- Проверить зависимости по manifest/lockfile/imports, а не по распространённости библиотеки.
- Для ошибки воспроизвести симптом и найти причину до исправления.
- Для стороннего API или CI сверить поведение с актуальной документацией производителя.
- Не проводить широкое исследование, если цель и пути уже названы.

Результат: причина или точка изменения подтверждена, объём работ ограничен задачей.

## 3. Спланировать

Для нетривиальной работы использовать короткий список:

```text
1. <шаг> → проверка: <наблюдаемый результат>
2. <шаг> → проверка: <наблюдаемый результат>
3. Финальный diff/status → проверка: только нужные файлы, нет артефактов
```

Для большой или прерываемой задачи создать документы по [правилам](documentation-and-process.md). Для простого изменения достаточно плана в рабочем интерфейсе.

Результат: у каждого шага есть проверка, а не только действие.

## 4. Реализовать минимально

- Сохранять архитектуру, именование и стиль проекта.
- Сначала воспроизвести баг тестом, если инфраструктура это позволяет.
- Не рефакторить соседний код и не добавлять возможности на будущее.
- Не удалять посторонние дефекты; сообщить о них отдельно.
- При изменении контракта перечислить все его элементы и потребителей.
- Выполнять шаги плана и сразу отмечать проверенные результаты.

Результат: изменение закрывает запрос полностью и не содержит посторонних правок.

## 5. Проверить

Проверка идёт от быстрой и локальной к реальному сценарию:

1. Тест изменения или регрессионный тест.
2. Затронутые unit/integration-тесты.
3. Стандартные build/test/lint проекта.
4. Реальный пользовательский сценарий, внешний контракт или миграция.
5. Финальный `git diff` и `git status` каждого затронутого репозитория.

Если проверка невозможна, зафиксировать причину и конкретную непроверенную часть. Нельзя называть работу завершённой при красных относящихся к ней проверках.

Результат: подтверждено поведение на финальном состоянии, а не только компиляция.

## 6. Передать результат

В финальном ответе:

- что изменено и где;
- какие проверки выполнены и их результат;
- что не проверено и почему;
- какие внешние действия выполнены или заблокированы;
- посторонние находки, если они важны пользователю.

Не пересказывать хронологию рассуждений. Для длительной работы обновить `log.md` и `next-steps.md`.

## Диагностика без исправления

Если пользователь спрашивает «почему не работает», сначала найти причину и отделить подтверждённые факты от гипотез. Исправлять только тогда, когда это входит в запрос. Знакомый текст ошибки не считается доказательством знакомой причины.

## Длительная задача

- Вести журнал по датам: цель, затронутые файлы, выводы, проверки, блокеры.
- Оставлять следующий конкретный шаг и текущее состояние для новой сессии.
- Не превращать журнал в поток рассуждений.
- Постоянные решения переносить в ADR и документацию; временные файлы не разбрасывать по продуктовым репозиториям.
