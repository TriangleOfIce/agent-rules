# Kotlin и Kotlin Multiplatform

Эти правила применяются только там, где соответствует стек проекта. Локальная архитектура и команды проекта важнее типового маршрута.

## Архитектура и код

- Общая бизнес-логика находится в `commonMain`; платформенные API не попадают туда.
- Предпочитать интерфейсы и dependency injection; `expect/actual` использовать только при необходимости и изолировать платформенную реализацию в её source set.
- Clean/MVI/MVVM и структуру пакетов выбирает существующий модуль, а не универсальный шаблон.
- Следовать официальным Kotlin coding conventions и `.editorconfig` проекта.
- Для асинхронности и реактивного состояния использовать принятые в проекте coroutines и `Flow`/`StateFlow`.
- Не поглощать `CancellationException`; особенно проверять `runCatching` и широкий `catch (e: Exception)` в suspend-коде.
- Не использовать исключения для обычного control flow; следовать принятой модели ошибок проекта.
- Предпочитать `val`, неизменяемые данные и read-only коллекции.
- У публичного API указывать явные типы возврата и короткий конкретный KDoc.
- Выбирать структуры данных по операциям доступа; не использовать наивные вложенные проходы по растущим коллекциям без необходимости.
- Не оставлять `TODO` в production-коде без ссылки на задачу, если это требует проект.

## Тесты

- Общая логика — `commonTest`.
- Основа быстрых проверок для presentation/business logic — integration-тесты presentation model + interactors с фейками репозиториев.
- Реализации репозиториев тестируются отдельно с подменой сервера, БД и системных сервисов.
- Фейки и стабы предпочтительнее моков. Моки нужны для проверки вызовов или внешних зависимостей, для которых фейк неоправданно сложен.
- Android host-тесты и instrumented-тесты используются по назначению; iOS — соответствующие `iosTest`-таргеты.
- Изменения `expect/actual` и платформенных адаптеров не считаются проверенными только быстрыми JVM-тестами.
- Имя теста описывает сценарий; один тест выполняет минимум действий и проверяет одно поведение. Параметризация убирает дублирование входных данных.
- Тестовый фреймворк и версии выбираются по существующему build, а не добавляются автоматически.

## Gradle и проверка

Перед запуском убедиться, что task существует в данном build. Типовые команды являются примерами, не универсальной командой:

```bash
./gradlew build
./gradlew allTests
./gradlew testDebugUnitTest
./gradlew iosSimulatorArm64Test
```

`commonTest` — source set, а не гарантированная Gradle-задача: общие тесты запускаются через platform test tasks. Быстрый desktop/JVM task используется, только если он действительно определён проектом.

После изменения `.proto`, ресурсов или другого генерируемого источника выполняется предусмотренная проектом генерация; сгенерированные файлы не редактируются вручную.

## Публичный API и зависимости

- Совместимое добавление API обычно требует MINOR, ломающее — MAJOR, отсутствие видимого изменения API — PATCH по SemVer и правилам проекта.
- Успешный обычный `check` не доказывает бинарную совместимость: нужна предусмотренная проектом проверка API.
- Ломающее изменение общего контракта сначала согласовывается, затем обновляются все затронутые потребители.
- В стабильной ветке потребителя не остаются local/branch/snapshot-зависимости, если это запрещено release-процессом.
- Release-проверки должны зависеть от проверок API и версии; если текущий CI этого не делает, это отдельная задача, а не повод молча менять инфраструктуру вместе с фичей.
